# BUG-034 – Records saved before the validation fixes are never checked

| Field | Value |
|---|---|
| Module / Category | Database / Data Integrity |
| Severity / Priority | High / Medium |
| Reported by / Fixed by | Mayank |
| Status | Fixed |

## How it was found
Many of the fixes (BUG-024, -029, -030, ...) only stop *new* bad data. A database that was in use before them can still hold duplicate registration numbers in different case, over-full rooms, two active rooms for one student, orphan rows, and so on, and nothing ever looked. This was on the known-limitations list ("existing saved records are not re-validated").

## Root cause
Validation runs only when something is written; existing data was never inspected.

## Fix
New read-only `app/database/check_data.py`:
- `run_checks()` reports: duplicate registration numbers (ignoring case), rooms over capacity, students with more than one active room, allocations or complaints pointing at missing rows, open leaves for students with no active room, student accounts not linked to a student, and student names / registration numbers / contact numbers that today's rules reject.
- `python -m app.database.check_data` prints the findings.
- `main.run` runs it at start-up and writes each finding to the error log (module `Database`, type `DataQuality`). It never changes data.

## Test
`tests/test_check_data.py` (clean database, crafted bad database, error-log entries; the bad-database test fails if a check is removed). The checker also reports nothing on a freshly loaded real-class database. Full suite: 240 tests OK.

## Not covered
It reports problems but does not repair them; fixing a duplicate or an over-full room needs a person to decide which record is right.
