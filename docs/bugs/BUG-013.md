# BUG-013 — Allocation screen lists students who already have a room and rooms that are full

| Field | Value |
|---|---|
| Module / Category | Allocation / UI/UX |
| Severity / Priority | Low / Medium |
| Status | Fixed (close it in the Bug screen after re-testing) |

## How it was found
A script drove the real Allocation, Leave, Complaint and Room screens (Xvfb, handlers called as the buttons would). On the Allocation screen:

```
students offered: 3   rooms offered: 2
allocate Aa Bb -> A1          (ok)
students offered: 3   rooms offered: 2      <- Aa Bb and the full room A1 are still offered
allocate Aa Bb again          -> "This student already has an active room allocation..."
```

The service rejected the mistake correctly, but the screen kept offering choices it knew would fail, and a released bed did not reappear until the screen was reopened.

## Root cause
`refresh_dropdowns` listed every student and every room, and `on_allocate` / `on_release` only refreshed the table, not the dropdowns.

## Fix
`app/screens/allocation_screen.py`:
- the student list shows only students without an active room;
- the room list shows only rooms with a free bed, labelled with usage (for example `A2 (Double, 1/2 used)`);
- both lists are rebuilt after every allocate and release, and a selection that is no longer valid is cleared.

The service-level checks are unchanged and still run.

## Test
`tests/test_allocation_screen_ui.py` — `test_bug_013_*` (allocated student and full room leave the lists, a partly full room stays with usage shown, release brings both back). They need a display and are skipped without one. With the filters removed, a test fails. Full suite: 206 tests.
