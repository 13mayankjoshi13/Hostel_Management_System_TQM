# BUG-024 – Simultaneous allocations can overfill a room

| Field | Value |
|---|---|
| Module / Category | Allocation / Data Integrity |
| Severity / Priority | High / High |
| Reported by / Fixed by | Mayank |
| Status | Fixed |

## How it was found
Ran 8 `allocate_room` calls at once (threads) on a capacity-1 room. In repeated runs the room ended with 2 active students; the message even read "full capacity (2/1)".

## Root cause
`allocate_room` checked capacity and then inserted under SQLite's default deferred transaction, so two callers could both pass the check before either wrote. Nothing in the schema stopped a second active allocation for one student either.

## Fix
- `app/services/allocation_service.py`: `BEGIN IMMEDIATE` at the start, so the checks and the insert hold the write lock together.
- `app/database/db.py`: partial unique indexes, one active allocation per student and one open leave per student. If an existing database already has duplicates the index is skipped rather than blocking start-up.

## Test
`tests/test_bug_fixes.py::test_bug_024_simultaneous_allocations_never_exceed_capacity` (8 threads, exactly 1 succeeds; the index rejects a second active allocation). Fails without the fix in repeated runs. Full suite: 222 tests OK.

## Not covered
Other write paths (e.g. leave recording) are protected only by the new index, not by an immediate transaction.
