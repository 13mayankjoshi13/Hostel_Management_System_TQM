# BUG-041 – Log rows are lost while a log CSV is open in Excel

| Field | Value |
|---|---|
| Module / Category | Other (logging) / Data Integrity |
| Severity / Priority | High / High |
| Reported by / Fixed by | Mayank |
| Status | Fixed |

## How it was found
The error, audit and defect CSVs are the project's evidence, and the natural thing to do with them is open them in Excel to review. On Windows, Excel locks the file, so the logger's append fails with `PermissionError`. The logger "never raises", which meant the error was swallowed: every action done while the file was open left no audit or error trace.

## Root cause
`_append_row` had no fallback when the CSV could not be written.

## Fix
`app/utils/logging_service.py`: a row that cannot be written is queued in `<log>.csv.pending`; the next time the CSV is writable the queued rows are added first, in order, then the new row, and the pending file is removed. Formula neutralisation (BUG-020) still applies when they are added. If even the pending file cannot be written the call still returns "unlogged" without raising.

## Test
`tests/test_log_resilience.py::test_bug_041_*` simulates the lock (fails without the fix). `tests/test_logging.py` "unwritable" tests now make the pending file unwritable as well. Full suite: 252 tests OK.
