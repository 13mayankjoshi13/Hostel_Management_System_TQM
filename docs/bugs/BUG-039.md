# BUG-039 – Times shown in the app are UTC, and resolved/returned times used a different clock

| Field | Value |
|---|---|
| Module / Category | Other (all screens and exports) / Data Integrity |
| Severity / Priority | High / High |
| Reported by / Fixed by | Mayank |
| Status | Fixed |

## How it was found
Comparing a record's database timestamp with the computer's clock. SQLite's `datetime('now')` is UTC, and the Complaints, Allocation, Users and My Room/My Complaints screens (and the allotment CSV) showed it unchanged: 5 h 30 min behind India. `resolved_at` and `returned_at` were written with `datetime.now()` (local), so in India a complaint could look resolved 5.5 hours before it was logged.

## Root cause
Two clocks in one record, and no conversion before display.

## Fix
- `app/utils/timefmt.py`: UTC is the storage convention (`utc_now`), shown through `utc_to_local` / `localise_rows`.
- Resolved and returned times are now written in UTC (complaint resolve, leave return, release closing a leave).
- Services convert to local time on the way to the screens and the export: `get_all_complaints`, `get_active_allocations`, `list_users`, `my_room`, `my_complaints`.
- `db.py` converts older local-ISO resolved/returned values to UTC once (detected by the `T`, so repeating it is harmless).

## Test
`tests/test_timestamps.py` runs with `TZ=Asia/Kolkata` (conversion, new records show "now" in local time and resolved is not before created, old rows converted once). Fails without the fix. Full suite: 249 tests OK.

## Not covered
Audit and error CSV logs already use local time and are unchanged. Bug dates (`bugs.date`) are calendar dates and unchanged.
