# BUG-012 — Students screen loses the highlighted row after re-sorting while an edit is open

| Field | Value |
|---|---|
| Module / Category | UI / UI/UX |
| Severity / Priority | Low / Medium |
| Status | Fixed (close it in the Bug screen after re-testing) |

## How it was found
A script drove the real Students screen (Xvfb, handlers called as the buttons would): select a student, then change the Sort by box.

```
after resort: editing id 1, form shows "Charlie Brown", table selection = ()
```

The form and the Save Changes button stayed active for a student, but no row was highlighted. Saving then changes a student the user can no longer see selected.

## Root cause
`refresh()` deleted and rebuilt every table row, which clears the selection, and never restored the selection the edit form was tied to.

## Fix
`app/screens/student_screen.py`, `refresh()`: after rebuilding, the row of the student being edited is selected again and scrolled into view. A `_restoring` flag stops that re-selection from overwriting what the user has typed in the form. If the student no longer exists, the edit state is cleared and Save Changes is disabled.

## Test
`tests/test_student_screen_ui.py` — `test_bug_012_*` (selection kept after re-sort, unsaved typing survives, edit state cleared if the student is gone). These need a display and are skipped automatically without one. With the fix removed, the selection test fails. Full suite: 203 tests, 3 skipped without a display.
