# BUG-031 – No backup: a damaged database file loses every record

| Field | Value |
|---|---|
| Module / Category | Database / Data Integrity |
| Severity / Priority | Critical / High |
| Reported by / Fixed by | Mayank |
| Status | Fixed |

## How it was found
Reviewing failure paths after BUG-027: every student, room, allocation, complaint and account is in one SQLite file (`app/database/hostel.db`) and nothing makes a copy. A damaged or deleted file means total loss.

## Root cause
No backup or restore existed.

## Fix
New `app/database/backup.py`:
- `create_backup()` runs at start-up (`main.run`): one backup per calendar day using SQLite's online backup, kept for 7 days in `app/database/backups/`.
- A database that fails `PRAGMA integrity_check` is not backed up (and is logged as Critical), so a damaged file can never push out good copies.
- `restore_backup()` / `python -m app.database.backup restore FILE` checks the backup is healthy and keeps the current file as `hostel.db.before_restore`. `python -m app.database.backup` lists backups.
- The start-up failure message (BUG-027) now says how to restore.

## Test
`tests/test_backup.py` (3 tests: daily/restore, pruning, damaged files). Pruning test fails without the fix. `tests/test_startup_errors.py` now stubs the backup so tests never touch a real database. Full suite: 234 tests OK.

## Not covered
Backups sit on the same disk as the database, so they protect against a damaged file, not a lost computer. They contain real student data and must not be committed to Git.
